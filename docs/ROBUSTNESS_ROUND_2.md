# ズーケッチ 堅牢化第2弾の検証手順

比較の基準は `1042758`。本番と同じ base でビルドし、同じ Mac、Node.js 24、同じ Playwright のブラウザで比較する。端末プロファイル、帯域制限、合成カメラで得た結果は実機の結果と区別する。

## 起動と認識の計測

`tools/recognition/performance.mjs` に公開用のビルドフォルダーと、固定リビジョンのCLIPファイルのフォルダーを渡す。使用するリビジョンとファイルは [性能チェックのGitHub Actions](../.github/workflows/performance.yml) に記載している。

```sh
npm run build
node tools/recognition/performance.mjs dist /path/to/clip-files > performance.json
node tools/recognition/performance-budget.mjs performance.json
```

起動は冷キャッシュで、タイトルの開始ボタンの描画までに完了した同一オリジンの通信を計測する。Adobe Fontsはローカル計測から除く。CLIPは実際のモデルを使い、モデルファイルが端末内キャッシュにある状態の準備と、見本写真の推論を分ける。

## 同条件で比べた起動とYOLOX

Apple M2のChromiumで同じモデルと公開用成果物を使用したローカル計測。

| 測定                       | 第1弾（1042758） |     第2弾 |
| -------------------------- | ---------------: | --------: |
| タイトル表示までの初回転送 |        215,642 B | 169,681 B |
| タイトル表示               |         251.3 ms |  218.0 ms |
| YOLOXのモデル取得          |          31.2 ms |   28.7 ms |
| YOLOXのWorker準備          |         282.8 ms |  222.0 ms |
| YOLOXの1回の推論           |          47.2 ms |   42.7 ms |

初回転送の変更前上位は、タイトルのJS 174,956 B、CSS 16,589 B、タグラインSVG 6,562 B、開始SVG 3,474 B、継続SVG 3,096 B。タイトルのJSを128,964 Bに削減。初期の300ミリ秒フェードをCSSに移し、比較画面のライブラリは画面を開いたときに読み込む。

この計測は制御したローカル配信で行った。以前の実測値（モデル取得376 ms、Worker準備385 ms）とは配信条件が異なる。Worker準備は再実行で遅くなる回もあり、132 ms／255 msへの回復を同じ条件で確認できていない。Cloudflare向けのYOLOXは可逆圧縮により3,659,407 Bから3,386,540 Bに削減した。

## CLIPの実モデル計測

| 測定                           | 第1弾（1042758） |       第2弾 |
| ------------------------------ | ---------------: | ----------: |
| 通常・キャッシュからの準備     |         673.7 ms |  2,787.5 ms |
| 通常・1枚目                    |       5,172.4 ms | 10,291.8 ms |
| 通常・3枚の中央値              |       9,412.0 ms |  8,237.8 ms |
| 制約あり・キャッシュからの準備 |       1,421.8 ms |  1,334.1 ms |
| 制約あり・1枚目                |      10,557.9 ms |  7,667.2 ms |
| 制約あり・3枚の中央値          |      10,068.7 ms |  6,716.4 ms |

制約ありはChromiumのページにCPU 4倍減速を指定し、Workerから見えるコア数を2にした。実コアの固定とWorker自体の速度低下は未確認。並行して走る試験の負荷が異なるため、低スペック端末の実測値や変更による高速化としては扱えない。CLIPは旧版の写真候補用で、現行の標準撮影フローはYOLOXを使う。

GitHub Actionsでは同一オリジンの初回転送185,000 B、開始ボタン表示1,000 ms、YOLOX推論200 ms、CLIP推論20,000 ms（通常）と30,000 ms（制約あり）を上限にする。計測値が欠けた場合も失敗する。

## 端末相当と低速回線

小型iPhone相当のWebKitとGalaxy相当のChromiumで、見本カメラから実YOLOXの検出、撮影、タッチ描画、保存を確認した。3G相当のChromiumでは、変更前は初回のWASM取得中に20秒の準備期限が切れ、100秒の待機でも白枠が出なかった。変更後はタイトルが1,724 msで表示され、モデル取得の503を1回入れた状態でカメラを開いてから109,084 msで白枠が表示された。公開用のローカルビルドを帯域制限している。準備後の推論1回の期限は8秒。送信は20秒で応答待ちを打ち切り、同じ記録IDで再送した。

更新試験では意図的に配信元を入れ替え、旧方式で新旧が混在することを再現した。新版同士ではChromiumとWebKitで旧版のタブを保ち、最後の旧タブが閉じた後に新版が有効になった。旧方式を使っているタブも、初回移行時は一度全部閉じると新版に更新できる。

## 30分の連続試験

公開用ビルドをローカルで起動し、公開URLのパスに合わせて試験する。見本画像をカメラ映像として与え、実YOLOXのライブ検出をしばらく動かした後、撮影、動物名の確認、描画、保存、撮影画面への復帰を繰り返す。送信はローカルで捕捉する。

```sh
npm run build
npm run preview -- --host 127.0.0.1 --port 4175 --strictPort
# 別のターミナルで実行
node tools/performance/mobile-soak.mjs http://127.0.0.1:4175/ soak.jsonl 30 50
```

記録するのはガベージコレクション後のChromiumページのJSヒープ、バッキングストレージ、DOMノード、Worker・映像トラックの作成・解放数、模擬送信とギャラリーの件数。OSから見たプロセス全体のメモリ、iPhoneでの発熱や温度を表す数値には使えない。

実機で確認する手順は [5〜10分の実機チェックリスト](DEVICE_CHECKLIST.md) を参照。
